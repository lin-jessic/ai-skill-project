# OpenShop AI V5｜智慧開店可行性評估助手

## 1. 目的與範圍

將市場研究、法規查核、財務分析、營運規劃與品質審查串成可追蹤、可重現的工作流程。
本 Skill 直接在支援 Skill 的 AI 工具中執行，不需要網頁、FastAPI、PWA 或瀏覽器伺服器。
沿用 V4 的資料來源、分析工具及風險規則；V3.1、V4 網頁保留為歷史成果，不作為執行前提。
本 Skill 提供決策輔助，不保證獲利、合法核准或開幕日期。

## 2. 啟動邊界

### 應啟動

- 使用者想開實體店面並要求整體規劃，或同時需要市場、法規、財務、營運與程序中至少兩類評估。
- 提供業態、地點、預算、坪數或商圈資料，要求綜合可行性評估。
- 使用口語描述開店困難，例如想租店面賣飲料但不知道客人多不多、成本及開店準備事項。
- 已在本次開店工作流程中要求修改地點、成本、權重或營運條件時，更新受影響階段。

### 不應啟動

- 單純撰寫 IG 宣傳文案、翻譯菜單、一般法律糾紛、記帳教學或股市分析。
- 只有店家關鍵字而沒有開店規劃意圖，不因關鍵字相同誤啟動。
- 只詢問孤立的單一專業問題時，直接回答該問題，不強制執行全流程。
- 混合請求只將開店部分納入本 Skill。

## 3. 執行環境與工具定位

先定位本 Skill 及專案目錄，檢查實際存在的腳本、參考資料及依賴，再執行。
建議將正式 Skill 安裝於工作區的 `.agents/skills/store-opening-advisor/`，只啟用一套同用途版本。
V5 尚未整合完成時，可在原 V4 目錄重用以下已存在的工具；不得宣稱新版適配層或五角色程式已存在。
Python 依賴以實際 import 與 requirements 檔為準；不為純命令列任務強制安裝網頁依賴。

| V4 既有資源 | 用途 |
|---|---|
| `scripts/download_official.py` | 官方資料取得與來源紀錄 |
| `scripts/studio_engine.py` | `parse_upload`、`rank_places`、`daily_simulation`、`legal_for`、`create_artifacts`、`save_artifacts`、`play_one_day` |
| `scripts/logic.py` | 既有分析輔助邏輯；先讀取實際介面 |
| `scripts/run_studio.py` | 原三階段命令列示範與回歸測試 |
| `scripts/run_pipeline.py` | 原 CLI 相容入口 |
| `references/data_sources.md` | 資料來源說明 |
| `references/verified_official_sources.md` | 官方來源索引；仍需確認時效 |
| `examples/DEMO_商圈資料_情境假設_非官方.csv` | 合成測試資料，不是官方統計 |

在 V4 目錄可執行：

```cmd
python -m scripts.download_official --check
python -m scripts.run_studio --help
python -m scripts.run_studio --input "examples/DEMO_商圈資料_情境假設_非官方.csv" --shop 手搖飲店 --city 桃園市 --output outputs/studio_cli
```

注意：原 CLI 只接受 input、shop、city、output，其他財務參數寫死在程式內。
不得以此 CLI 的預設預算、租金、行政區或開幕日冒充使用者條件。
正式任務應讀取既有函式簽章與 config 契約，使用實際參數呼叫，必要時以可核對的小型適配腳本處理。
原 `rank_places` 的 weights 預設為三元素；不得未核對實作就傳入四元素或宣稱四項獨立權重已支援。
原三階段工具產出只能作為分析證據，不能改名冒充五個 AI 角色的交接成果。

## 4. 執行規則與需求釐清

1. 擷取業態 `business_type`、地點 `location`、行政區 `district`、候選地點、坪數或 `floor_area_sqm`、預算 `budget_twd`、目標開幕日、營運偏好及輸入資料。
2. 地點或業態缺漏且無法合理推進時，最多詢問三個精準問題；其他缺漏可依使用者同意採假設，明確列出。未知值使用 null，不當作 0。
3. 每次執行建立獨立 `outputs/<run_id>/`；保存原始資料，不覆蓋歷史結果。
4. 依序載入角色指令並執行。平台支援獨立代理時可委派，否則由同一 AI 依序執行五種職責，不宣稱啟動了五個獨立模型。
5. 角色檔若尚未建立，以本文件第 5 節的完整分工執行；若舊角色檔與本規格衝突，不載入舊指令，記錄限制。
6. 每個角色必須實際讀取上游輸出，保存自身結果；不得只生成角色名稱與空報告。
7. 數字、法規、時間與建議皆區分已查證資料、使用者輸入、假設、推導及未確認項目。

## 5. 五角色工作流程

### Agent 1｜市場與商圈研究員

- 建議角色檔：`agents/01_market_researcher.md`。
- 輸入：開店需求、候選地點、官方資料或使用者提供的 CSV/JSON。
- 任務：依需要下載資料、檢查欄位與品質、清理並對齊行政區及時間；分析人口結構、競品、交通代理指標、租金與潛在客群；比較商圈並說明排名及限制。
- 輸出：`01_market_report.json`、清理資料與商圈比較表（有足夠資料時）。
- 必填：來源、品質檢查、候選地點、權重與分數組成、推薦原因、客群假設、缺漏與風險。
- 交接：將候選地點及店型條件交給 Agent 2；市場參數交給 Agent 3、4。

### Agent 2｜法規與證照顧問

- 建議角色檔：`agents/02_legal_advisor.md`（須與新版規格同步）。
- 輸入：Agent 1 報告、使用者補充條件、官方法規來源。
- 任務：查核土地使用、商業／公司登記、稅籍、食品業者登錄、消防、建管、勞動及業態適用規範；逐項列出機關、文件、前置條件、預估天數與待確認事項。
- 輸出：`02_legal_checklist.json`。
- 必填：法源及日期、適用範圍、風險、申辦行動、主管機關、可能的設備成本與時程限制；未知成本不捏造。
- 交接：將法規限制及未確認風險交給 Agent 3、4。

### Agent 3｜財務與成本分析師

- 建議角色檔：`agents/03_financial_analyst.md`。
- 輸入：Agent 1、2 報告、預算、使用者成本與營收參數。
- 任務：使用 Python 試算開店資金、押金、裝修、設備、人事、租金、原物料、外送及固定／變動成本；計算損益兩平、現金流與保守／一般／樂觀情境。
- 輸出：`03_financial_report.json`、財務情境比較 CSV（可計算時）。
- 必填：完整輸入、公式、初始支出、月成本與營收、單筆貢獻、損益兩平、預算缺口及敏感度；不將模擬當成市場預測。
- 交接：將財務限制及各情境交給 Agent 4。

### Agent 4｜開店與營運規劃師

- 建議角色檔：`agents/04_business_planner.md`。
- 輸入：Agent 1–3 報告及使用者營運偏好。
- 任務：規劃店型定位、設備、員工、商品或食材、營業時段、內用／外帶／外送策略及開店程序；按需求使用逐日模擬，並整理依賴關係及甘特表。
- 輸出：`04_business_plan.json`、`04_opening_schedule.md`。
- 必填：設備及人力、操作建議、申辦機關、文件、前置條件、預估工作天、營運參數與模擬限制。
- 交接：若方案改變成本，退回 Agent 3 重算；地點或業態變更時重新確認 Agent 1、2；將最終方案交給 Agent 5。

### Agent 5｜綜合審查與決策顧問

- 建議角色檔：`agents/05_reviewer.md`。
- 輸入：Agent 1–4 產出、原始資料、計算參數及執行紀錄。
- 任務：獨立抽查資料來源、重算商圈分數及財務結果；檢查預算、法規與營運方案一致性、申辦依賴、風險及報告完整性。
- 輸出：`05_audit_report.json`、`06_final_report.md`。
- 必填：逐項檢查結果、重算數值、差異、錯誤原因、修正紀錄、阻擋事項、最終審查狀態。
- 發現錯誤時退回責任角色修正，再重跑受影響的下游階段；最多兩輪自動修正，仍無法處理則標記 blocked 或 partial 並說明原因，不虛報通過。

## 7. 分析及驗證規則

### 7.1 官方資料與清理

- 依需求使用官方下載器，先取得必要授權及確認網路可用。原 V4 下載結果在 `data/raw/`，manifest 在 `data/official_download_manifest.json`。
- 官方資料下載後須依實際欄位清理、轉換、對齊期間及地理粒度，才可用於分析。若沒有現成 ETL，明確記錄轉換步驟或限制。
- 區分官方原始資料、衍生資料、使用者提供資料及合成資料；不得把資料來源自述當作驗證證據。
- CSV/JSON 檢查編碼、缺欄、缺值、重複、非有限數、負值、單位與資料期間。無法可靠處理時停止受影響的評分，不以 0 代替未知數。
- 保留來源、實際雜湊與清理紀錄；不得偽造下載或檔案。

### 7.2 商圈比較

- 既有資料欄位：district、population、competitors、footfall、rent；確認實際解析器支援的別名及單位。
- 核對 V4 的權重實作，再呈現人口、交通、競品、租金的實際分數與貢獻。
- 建議可調整四項獨立權重，總和須為 100%；若原函式不支援，使用經測試的適配或明示沿用原規則，不虛報新功能。
- 交代正規化、同值處理、正反向指標與權重假設；比較不同權重下排名是否改變。
- 人口及交通運量只是代理指標，不能直接等同實際客流；競品數不代表真實競爭強度，商圈分數不代表開店成功率。
- 只有一個候選地點時提供概況，不宣稱其排名優於未比較地點。

### 7.3 財務與營運

- 以新台幣計算，區分一次性支出、流動資金、月固定成本與變動成本，避免重複計入。
- P 為客單價、V 為每筆基礎變動成本、s 為外送比例、r 為外送抽成率、C 為外送額外包裝費、Q 為每日交易量、D 為每月營業天數、F 為月固定成本。
- 單筆貢獻 = P - V - s × (P × r + C)；月營收 = P × Q × D；月損益 = 單筆貢獻 × Q × D - F。
- 每日損益兩平交易數 = ceil(F / 單筆貢獻 / D)。單筆貢獻非正時不得給出有限損益兩平量。
- 上述為統一情境公式；若既有工具公式不同，核對差異、記錄並避免混用。未包含稅、折舊、利息等項目時註明。
- 內用、外帶、外送比例總和 100%；每日交易量、單價、營業日等參數須在合理範圍。
- 模擬記錄情境參數、期間及隨機種子；原物料、天氣等事件須標記假設。
- 選址、法規及營運方案應使用同一組有效條件；成本改變必須重新計算受影響的結果。

### 7.4 法規與風險

- 每項法規包含 item、source、source_date、checked_at、risk、authority、action_required、documents、prerequisites、estimated_workdays、needs_authority_confirmation。
- high：可能阻止營業或涉及重大違規；medium：需補件、變更或確認；low：一般行政提醒。
- 法規來源無日期時標記 source_date_missing；無法查證最新規定時列待確認，不假裝已查證。
- 高風險項目無對應機關或行動時，最終審查必須 blocked；個案核准未確認時不得宣稱可合法開店。
- 核對預算是否涵蓋適用的申辦、消防、建管、裝修、設備及預備金。

  02_legal_checklist.json
  03_financial_report.json

最終報告包含需求摘要、資料來源與品質、商圈及客群、法規、財務、營運、開店排程、審查與限制。
至少抽查一筆原始數值、重算一個商圈分數（資料足夠時）、重算一組財務情境，並核對上游檔案與法規行動矩陣。
審查狀態使用 pass、pass_with_conditions、blocked，說明依據；pass 不代表主管機關核准。
回覆先以 3–6 行摘要交代目前結果與限制，再提供角色成果、實際檔案路徑、關鍵建議及待確認事項。

## 9. A/B/C 啟動測試

在不同的新對話測試，避免先指定 Skill 名稱或手動要求讀取 SKILL.md。

| 測試 | 自然語言提示詞 | 預期 |
|---|---|---|
| A | 我想在桃園開手搖飲店，預算80萬元，幫我比較商圈、成本、法規及開店流程。 | 自動選用並執行完整流程 |
| B | 手上有80萬，想在桃園租店面賣飲料，不知道哪裡客人多、每天要賣多少才不賠錢，還需要準備什麼。 | 改寫後仍自動選用 |
| C | 幫我寫一篇手搖飲店的新品 Instagram 宣傳文案。 | 不啟動本 Skill |

A、B 使用相同來源的可重現資料；可預先放置範例資料，但不在測試提示詞強制呼叫 Skill。
保存平台選用或載入紀錄、實際工具命令、角色交接、成果與錯誤；手動觸發須獨立標註。
execution_log.json 只記錄實際執行，不可單靠 AI 自述或自建 log 聲稱平台自動觸發。
若平台無法提供載入證據，誠實記錄限制。測試失敗時修改 description 或流程並保留前後紀錄。
